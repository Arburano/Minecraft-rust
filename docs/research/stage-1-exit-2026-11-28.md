# Stage 1 exit review (T1-20)

Date: 2026-11-28. Exit criterion ([roadmap](../process/roadmap.md)): 60 FPS on the iGPU (Vega 10) at 12 chunks with 1% low ≥ 45, RAM ≤ 1.5 GB without LOD (internal budget 1 GiB), 30 minutes of walking without frame spikes > 33 ms, start to menu ≤ 5 s.

Input: the T1-15 laptop runs of 2026-11-27 ([summary](stage-1-exit-2026-11-27/summary.md), raw `summary-*.txt` in the same folder) and the stage 1 rows of [performance-budgets.md](../process/performance-budgets.md).

Status legend (as in the [stage 0 review](stage-0-exit-2026-11-21.md)): **Met**: measured within target. **Deviation**: measured and missing the target; the target is kept and a follow-up is planned. **Later**: can only be measured in a later stage.

## Measurement conditions

- ASUS TUF FX505DU, Ryzen 7 3750H, Windows 11, bare metal, AC power. Vega 10 (driver 27.20.1032.2) and GTX 1660 Ti (driver 32.0.15.5597), both DX12, path `PullingIndexed`.
- Release build of commit `cff0936`, `scripts/stage1_exit.ps1`: 3 × 1800 s on the Vega 10 and 1 × 1800 s on the GTX 1660 Ti, each after a 30 s warm-up, runs back to back.
- Route: `client --bench-route`, fresh world seed 12345, a 1000-block square flown 12 blocks above the ground at ≈ 5.5 blocks/s (9,983 blocks per run). The terrain ahead is always new, so generation, lighting, meshing and upload run all the time.
- Profile **High (16 chunks)**, not the 12 chunks of the criterion. 16 chunks is the heavier load (≈ 1.8× the columns), so a pass at 16 counts as a pass at 12 for FPS and RAM. A miss at 16 is not automatically a miss at 12 — see the spike section.
- One machine, one run per configuration except the Vega 10 (3 runs). CPU frequency was not pinned; the third Vega run started after one hour of continuous load (T0-16 saw this laptop drop to base clock after ≈ 35 minutes).

### Notes on the numbers

- **1% low in Vega run 3 (50.9 FPS, p99 16.6 ms).** Runs 1 and 2 have p99 7.9 / 6.0 ms. Run 3 is the third consecutive 30-minute run, which fits the thermal/base-clock drop T0-16 saw; it is still above 45. This is an inference from one run, not a measured cause. A repeat after a cool-down would confirm it; it does not change the verdict.
- **RAM** is the process physical memory (`memory_stats`, the Windows working set) sampled once per second. On the Vega 10 the GPU memory is shared system memory; the driver's allocations for our buffers are not necessarily in our working set. The terrain quad buffer has a fixed capacity, so that part is bounded, but it is not in these numbers.
- **Spikes are rare but real.** 36–189 frames over 33 ms out of 464k–532k frames (0.007–0.04%) — about one every 10–50 s. The maxima cluster at 95–120 ms on both GPUs, which points to CPU-side main-thread work rather than GPU load (the GTX 1660 Ti is ≈ 3.5× faster on the GPU side, T1-11, yet its worst frame is only ≈ 20% shorter).

## Frame spikes: what is known

The route stresses the loader far more than walking does: at 16 chunks and ≈ 5.5 blocks/s a new row of ≈ 33 columns enters the radius every ≈ 3 s, and nothing is ever loaded twice. The criterion says "30 minutes of walking", so the route is a harsher test than the criterion; we cannot tell from these runs whether walking at 12 chunks would be spike-free.

The harness records only frame times, so the spikes cannot be attributed from the committed data. Work that runs on the main thread inside `App::frame` and can plausibly take ≈ 100 ms in one frame (to be checked, not established):

1. **Synchronous region-file reads.** `Session::update` gives the loader a source closure that calls `RegionStore::load_column` on the main thread (within the loader's tick budget) for each column it schedules. In the fresh bench world these are misses, but each one still opens or looks up a region file.
2. **Autosave on the main thread.** Every 30 s `Session::save` rewrites `world.toml` (no fsync; edited columns would add region writes with fsync, but the route edits nothing). 60 autosaves per run is the same order as the spike counts, but a small file write rarely takes 100 ms, so this is a weak candidate.
3. **Upload bursts.** `render_updates` hands all re-packed batches and changed light sections to the renderer in one frame; a burst after many columns finish together means many `queue.write_buffer` calls and light-atlas writes in one frame.
4. **Unload bookkeeping.** Columns leaving the radius go through `track_saves`/light removal in the same frame.
5. **Outside the engine:** driver shader/pipeline work, the Windows compositor, or background processes. One spike every 10–50 s is also the shape of OS background activity; the runs did not control it.

Follow-up: [T1-25](../../tasks/stage-1/T1-25-frame-spike-attribution.md) — attribute every frame over 33 ms (per-frame counters plus a Tracy capture of the route), fix the main-thread causes, and add a walking-speed route at 12 chunks that matches the criterion literally.

## Recommendation

**Exit stage 1: yes**, provided the owner accepts:

1. FPS, 1% low, RAM and start to menu are met on the Vega 10 with margin, at the heavier 16-chunk profile; the "Client RAM" row moves from Hypothesis to Measured.
2. The frame-spike criterion is **not met** (36–189 frames > 33 ms per 30 min, max ≈ 120 ms). The target stays unchanged and T1-25 attributes and fixes the spikes, running in parallel with stage 2. Stage 2 work already depends on the same main-thread loop (T2-02 replaces local loading with streaming), so fixing the main-thread stalls now also helps the network client.
3. Open question 1 keeps its "For now" value (no web client) or gets a new deadline.

The alternative is to keep stage 1 open until T1-25 shows a spike-free 30-minute walk. That is stricter and matches "feel wins" literally, but stage 2 is already running, so in practice it changes only the label, not the work order.
