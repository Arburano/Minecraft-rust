## Summary

- **Met:** 14 rows; 5 of them VM-only: job scheduler, the two T0-11 network rows (a bare-metal shaped-link re-run is already in the stage 1 carry-over), epoch cost and mod cold start.
- **Deviations (5):**
  - World/mesh hot paths (`get`, `set`, gather + masks) are already in the stage 1 carry-over by owner decision (T0-16).
  - Hook dispatch and event cost are **not** in any carry-over yet. Proposed: a stage 3 optimization task before the stage 3 exit criterion "hook ≤ 1 µs with epoch". Candidate directions: cheaper priority elevation, primitive/flat event encodings instead of strings, fewer canonical ABI allocations.
- **Hypotheses (3):** client RAM → stage 1; network CPU → stage 2; node RAM → stage 2/6. Mod cold start is no longer a hypothesis.
- **Later:** targets that by nature need the stage 1+ game.

- External dependency: T0-10 (lawyer, Microsoft API access). It does not block engine work. Development uses offline mode and the developer's own licensed assets. Nothing is launched publicly until the answers arrive.

## Recommendation

**Exit stage 0: yes**, provided the owner accepts:

1. Keeping the five deviation targets unchanged, with follow-ups in stage 1 (`get`/`set`/gather) and stage 3 (hook/event).
2. Moving the three remaining hypotheses to the stages named above.
3. Leaving T0-10 as an open external dependency.

Then part B of T0-17 creates the stage 1 backlog.
