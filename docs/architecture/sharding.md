# Шардування між нодами

Етап 6. Крейти: `server` + майбутні `gateway` і `coordinator` (створюються на етапі 6). ADR: 0009.

## Компоненти

```text
клієнт ══QUIC══► шлюз ──► нода A (клітини 0..k)
                    └──► нода B (клітини k+1..)
            координатор: карта клітина → нода, перерозподіл
            шина: NATS JetStream (або прямі канали нода↔нода)
            глобальні сервіси: чат, друзі, економіка, профілі (PostgreSQL)
```

- **Шлюз** тримає з'єднання клієнта, маршрутизує трафік до ноди-власника позиції гравця. Перехід між нодами для клієнта непомітний (без перепідключення).
- **Координатор** призначає клітини (напр. 512×512 блоків) нодам. Старт — статична сітка; динамічне перерозбиття (гаряча клітина ділиться) — пізніше.
- **Зони перекриття** шириною ≥ радіус зони видимості: нода бачить край сусіда лише для читання (тіньові копії сутностей), щоб гравці бачили одне одного через кордон.

## Правила

1. Тіньова копія — лише для показу. Будь-яка дія через кордон (удар, вибух, зміна блоку в зоні перекриття) — команда ноді-власнику; результат приходить із затримкою між нодами.
2. Кожна сутність має **номер власності** (u64), що росте при кожній передачі. Команда зі старим номером відкидається.
3. Передача (handoff): серіалізація компонентів → повідомлення з номером власності N+1 → прийом ідемпотентний (повтор не створює копію) → підтвердження → джерело перестає вважати себе власником. Сутність заморожена 1–2 тіки; інтерполяція приховує це від гравця.
4. Доставка «щонайменше один раз» (JetStream або прямий канал з підтвердженням) + ідемпотентність. Core NATS («не більше одного разу») і класичний 2PC (зависає при падінні координатора) не використовуємо.
5. Джерело правди про власника — журнал подій. Що саме (JetStream чи PostgreSQL з версією запису) — відкрите питання.

## Ціль передачі

≤ 1 тік (50 мс) і непомітно для гравця. Не «< 1 мс».

## Межі шардування

- 5 000 гравців / 500 на ноду = 10 нод лише за рівномірного розподілу.
- Гаряча точка (подія на 2 000 гравців в одному місці) шардуванням не розв'язується: потрібна політика інстансів і черг (рішення на рівні дизайну гри).

## Тести (вихід етапу 6)

- Дві ноди, RTT 100 мс, 1 000 переходів туди-назад: 0 дублікатів, 0 втрат, p99 ≤ 50 мс.
- 200 ботів стоять на межі нод: тік обох ≤ 25 мс.
- Падіння ноди під час передачі: після відновлення жодного дюпу предметів (10 000 автотестів).
